# I2 deviations: real-module Python integration

Task I2 built the real extension with test hooks (`maturin develop --features test-hooks`) on
CPython 3.14t (free-threaded) and ran the Python suite against it (`SONGBIRD_TEST_NATIVE=real`)
and against the pure-Python fake (`SONGBIRD_TEST_NATIVE=fake`). This file lists the root-cause fixes
that run found and the tests it added, with the reason for each.

## 1. Library fixes

* **The pump owns the queue's feed tasks (refines W5.md §8 and §6.5).** `TrackQueue` started each
  lazy encoded entry's feed with `loop.create_task`. Only the client's `cleanup()` cancelled it
  (`TrackQueue._close`). If an app dropped the client without disconnecting, the pump's weakref
  callback closed the connection, but nothing cancelled a feed that was still waiting on its source
  (a stalled HTTP or WebSocket reader, for example). That feed kept its `EncodedStream`, the
  `_Pump`, the `native.Connection` and its `ConnShared` / `Dispatch` / internal `PcmQueue` alive
  until the source yielded again. That could take indefinitely long.
  * New `_Pump.spawn(coro, *, name)` runs a helper task of the connection. `_Pump._shutdown`
    (T10) cancels every task spawned this way, whether or not the client still exists. `TrackQueue`
    starts its feeds through it, and `cleanup()` still cancels them as before.
  * Found by the new 100-cycle test (§3). With the old spawning, its `abandoned` path fails with
    the `Connection`, the `_Pump` and the `TrackQueue` still alive.
* **An encoded stream closed before its first byte is not probed (refines W4.md §7).** The decode
  thread called symphonia's probe at once. When a stream was opened and then closed or aborted
  before any data arrived, the probe read EOF. symphonia-core 0.5.5 (`probe.rs:298`) then logged
  `probe reach EOF at 0 bytes.` at ERROR, which reached the app as
  `discord.ext.songbird.native.symphonia_core.probe`. This happens in normal flows: a stream that
  is never written, a queued stream skipped before its feed produced data, or a disconnect.
  * `EncodedShared::wait_for_input` now waits until a byte arrives, the input is finished, or the
    stream closes. Only a close skips the probe, with `Outcome::Closed`, which was already the
    result.
  * An empty *finished* stream still probes and fails with `reason="error"`, as before.
  * *I3: this left a window. A close between `wait_for_input` and the probe's first read still
    logged the error. It showed up under CPU load and is closed in `I3.md` §4.*
  * Unit test: `tx::encoded::tests::a_stream_closed_before_its_first_byte_is_never_probed`. It
    uses a `cfg(test)` record of probed stream ids and fails without the fix.

## 2. Test hooks

* **`Harness.step()` and `MixerHarness.pull()` release the interpreter (`py.detach`).** In
  production, the ConnWorker runs on the RX runtime and the mixer runs on songbird's thread.
  Neither ever attaches to Python. The test hooks ran both while attached.
  * On a GIL build (cp314, and cp314t with `PYTHON_GIL=1`), a step decoding 20 speakers therefore
    held the GIL and blocked the event loop.
  * `test_loop_jitter_while_decoding` (p99 < 5 ms) measured that artefact. It failed in every run
    with the GIL enabled, at 7–10 ms.
  * Detached, it passes under the GIL and under heavy load. The free-threaded behaviour is
    unchanged.

## 3. Tests

* **`test_leaks.py::test_connect_close_cycles_return_to_baseline`** reproduces the 0.5 leak
  (§15.1 defect 1) against the 0.6 API, as the phase-3 "100× connect/disconnect leak loop".
  * **Each of the 100 cycles:**
    * builds fresh fake discord.py objects and connects through discord.py's own
      `Connectable.connect` (detached connection, test hooks);
    * maps a speaker;
    * opens a mixed, a per-user and a router stream, an event stream, a written playback pulled
      by `MixerHarness`, an encoded stream, an Opus stream, a memory track, a queued Opus entry and
      a queued encoded stream (fed a real WAV, then stalled on its source);
    * receives audio and events, then ends.
  * **How a cycle ends, in turn:** `disconnect()`, `disconnect(force=True)`, removal from the
    channel (`left_channel`), a terminal loss with `reconnect=False` (`lost`, with a best-effort
    leave), or an app that drops the client without disconnecting (`dropped`).
  * **Checks after each cycle:** every Python object is collected: client, connection, pump,
    queue, streams, router stream, playback, sinks, tracks and the chunk.
  * **Checks at the end:**
    * every `_debug_live_counts()` entry is back at its baseline;
    * no `SongbirdClient` or `native.Connection` is left in `gc.get_objects()`;
    * no ERROR record was logged under `discord.ext.songbird`.
  * The counters it relies on must rise during a cycle, so the test cannot pass vacuously:
    `ConnShared`, `SubQueue`, `EventQueue`, `PcmQueue`, `TrackFlags` and `LiveReader`. On the real
    module `ConnWorker`, `Dispatch`, `SsrcState`, `DecodeThread`, `SongbirdInput` and `DoneGuard`
    must rise too.
  * It runs on both the fake and the real module.
* **`test_threads.py::test_loop_jitter_while_decoding` takes the best of three 1 s windows.** The
  §13.5 bound stays p99 < 5 ms.
  * Run in isolation on the free-threaded build, the test failed about 2 runs in 15, with p99
    between 10 and 35 ms. An idle loop with no feeder and no decoding failed just as often (2 of
    30 windows, max 29 ms).
  * During the failing windows there was no GC, and the pump dispatched nothing. The spikes are
    OS timer and scheduling noise on the host.
  * The bound must now hold in one of three windows. The GIL-held step of §2 still fails all three
    (6–12 ms), so a real stall is still caught.
* `test_wake.py::test_taken_bell_cannot_be_reused` closes its read socket. It leaked a
  `ResourceWarning`; the library was not involved.
