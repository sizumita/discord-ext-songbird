# I3 deviations: the GIL build (CPython 3.14)

Task I3 built the extension with test hooks for the GIL-enabled CPython 3.14 (cp314) and ran the
Python suite there, in both modes, next to the free-threaded build (cp314t) that I2 used. This file
records what the run found and what changed, with the reason for each.

## 1. Setup

* A second virtualenv, `.venv-gil`, on Homebrew's CPython 3.14.9 (GIL build), synced from
  `uv.lock` (`UV_PROJECT_ENVIRONMENT=.venv-gil uv sync --all-extras --dev --no-install-project
  --frozen`). It is listed in `.git/info/exclude`, not in `.gitignore`.
* The extension is built into it with `maturin develop --features test-hooks`, using
  `VIRTUAL_ENV=.venv-gil`, `PYO3_PYTHON=.venv-gil/bin/python` and a separate
  `CARGO_TARGET_DIR` (`target/cp314-gil`), so switching interpreters does not rebuild pyo3 in the
  shared `target/`.
* The editable install puts `native.cpython-314-darwin.so` next to I2's
  `native.cpython-314t-darwin.so` in `py-src/discord/ext/songbird/`. Each interpreter loads its
  own file, so both environments stay usable at the same time (both files are ignored by `*.so`).

## 2. Deadlock audit under the GIL

The main risk on a GIL build is a native call that blocks while attached (holding the GIL) waiting
for a thread that needs the interpreter. Nothing of that shape was found, so the audit needed no
Rust change (the one Rust fix of this task, §4, is a logging race):

* No Rust-created thread can attach (G2), so a Rust thread never waits for the GIL.
* Every sbcore lock is a leaf held for µs, and no binding code creates Python objects, runs Python
  or calls `py.detach` while one is held: sbcore exposes no guards and takes no closures from the
  binding (the only binding closures, in `NativeTrack.control`, call `TrackRef` methods).
* The only blocking waits in sbcore that are not in tests are the decode thread's condvar waits.
  Python threads never block in a native call, except `_log_wait`, which parks detached.
* The binding's lazily initialised statics (`MONO_ANCHOR`, `EXC_TYPES`) are pyo3 `PyOnceLock`s,
  which detach while another thread initialises them. A `std` `OnceLock` whose initialiser calls
  Python would deadlock here.
* `Harness.step()` and `MixerHarness.pull()` already run detached (I2.md §2).

The suite passed on the first GIL run. It passed again with `sys.setswitchinterval(1e-6)` (a GIL
hand-off every microsecond), and once more with `gc.set_threshold(5, 1, 1)` added, which runs
collections, finalizers and weakref callbacks inside almost every allocation. The scratch runner
that set both is not committed.

## 3. Tests

* **`test_threads.py::test_gil_state_after_import` replaces `test_gil_stays_disabled_after_import`
  (the old test was vacuous).** The old test ran its child with `PYTHON_GIL=0`, and CI also exports
  `PYTHON_GIL=0` for 3.14t runs. `PYTHON_GIL=0` keeps the GIL off even after a module without
  `Py_mod_gil` asks for it, so the assertion held whatever the import did. A scratch C extension
  without the slot showed this: with `PYTHON_GIL=0` the old check passed, without it the GIL was
  re-enabled with a `RuntimeWarning`.
  * The new test runs its child with `PYTHON_GIL` removed (`run_isolated(env={"PYTHON_GIL": None})`;
    `run_isolated` now treats a `None` value as "unset").
  * On a free-threaded build it asserts `sys.flags.gil is None` (not forced),
    `sys._is_gil_enabled()` is `False` after importing discord, the package, numpy and pyarrow, and
    no "GIL has been enabled" warning was printed.
  * On a GIL build it asserts `sys._is_gil_enabled()` is `True`.
  * In both cases the loaded native module's file must end with this interpreter's `EXT_SUFFIX`,
    so a cp314t build cannot be loaded by mistake.
  * With the scratch extension imported from `sitecustomize`, the new test fails as it should.
  * It runs on both builds and in both modes; the old one was skipped on GIL builds.
* **`scripts/smoke.py` had the same blind spot.** `release.yml` exports `PYTHON_GIL=0` before
  running it on 3.14t. `check_gil()` now checks in-process only when `sys.flags.gil is None`, and
  otherwise re-runs the import in a child without `PYTHON_GIL`.
* **New `test_threads.py::test_cross_thread_load_and_a_foreign_close_never_deadlock`** covers §13.5's
  "no deadlock (watchdog)" item, which had no test of its own. It runs on both builds and in both
  modes.
  * **Concurrent load, about 1 s:**
    * the worker step with injected ticks;
    * the mixer pull;
    * three playback writers (bytes and base64), one of them also calling `clear()`, plus
      `stats()` and properties;
    * an encoded-stream writer and an Opus-stream sender;
    * two readers (mixed stream, per-user stream, events);
    * large `RawPcm` and `RawPcm.from_samples` constructions (the detached paths of §5.2);
    * a thread forcing `gc.collect()`;
    * the loop thread itself pausing and resuming a track.
  * The GIL changes hands every 10 µs meanwhile.
  * A foreign thread then closes the connection under that load.
  * **Checks:**
    * the close returns;
    * every thread finishes;
    * every thread made progress;
    * the loop never stalled for 2 s;
    * the streams report the close after draining what T6 left.
  * `faulthandler.dump_traceback_later(120, exit=True)` is the hard watchdog: a hang anywhere,
    including the loop thread, dumps every stack and ends the run instead of hanging CI.

## 4. Library fix: a close during the probe still logged an ERROR (refines I2.md §1)

* **Finding.** One of the first GIL runs, on a loaded host, failed
  `test_leaks.py::test_connect_close_cycles_return_to_baseline` once. With 14 CPU-bound processes
  on the 10-core host it failed again on the first try. The failure was three
  `discord.ext.songbird.native.symphonia_core.probe: probe reach EOF at 0 bytes.` records at ERROR.
* **Cause.** I2's `wait_for_input` skips the probe of a stream closed before its first byte. It
  does not cover a close that lands **after** `wait_for_input` saw bytes and **before** the probe's
  first read. `close_ring` frees the queued bytes, the probe's first `read` returns EOF, and
  symphonia logs at ERROR. A loaded host stretches that window, for example when the queued
  encoded stream of a leak cycle is closed by the disconnect while its decode thread is
  descheduled. The interpreter build plays no part: the decode thread never touches Python.
  * The same report appears for any close in the middle of a probe (`... at N bytes`).
  * Keeping the bytes until the probe ends is not an option: a close frees the ring (§10 T5,
    `close_ring`), and the probe of a stalled stream can wait on input indefinitely.
* **Fix.**
  * `ByteRingSource::read` calls the new `sbcore::log::mute_dependencies()` when it returns EOF
    because the ring was closed.
  * That flag is thread-local. From then on, the logger drops records **from that decode thread
    only** whose target is not this library's (`sbcore`, `discord_ext_songbird_native`).
  * Our own records, other threads, and the reports of a genuinely empty or undecodable *finished*
    stream (no close involved) are unaffected.
  * The flag dies with the thread, and each decode thread serves exactly one stream.
* **Tests.**
  * `log::tests::a_muted_thread_drops_other_crates_records_only`.
  * `tx::encoded::tests::a_close_between_the_wait_and_the_probe_mutes_symphonias_eof_report` uses a
    `cfg(test)` hook (`CLOSE_BEFORE_PROBE`) that closes the ring exactly in that window, and a
    `cfg(test)` record of each decode thread's muted state at exit (`MUTED_AT_EXIT`). It fails
    without the fix.
  * The empty-finished case asserts the thread stays unmuted.
  * With 14 CPU-bound processes, `test_leaks.py` went from failing on the first run to passing 6
    runs in a row.
* **`DecodeThread` is counted from the spawn (change).** The `LiveCounter` was created inside the
  thread, so a thread the OS had not scheduled yet (and that already held a worker slot) was
  missing from `_debug_live_counts()`. On a loaded host this could make the leak test's "this
  counter rose during the cycle" check fail for the first cycle. The counter is now created by
  `spawn_encoded_with` and moved into the thread. A failed spawn drops it with the closure.
